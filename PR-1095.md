_Requested by **Guy** · [project thread](https://claude.ai/code/project/chan_01TFAVQEVFL8KKQ8fhVfpfJo?thread=cmsg_01TFAVQEVFL8KKQ8fhVfpfJo8zVc1LYpAGvDAfoqPNiBtS)_

Every loot filter setting change rebuilds the whole filter (about 6,400 rules now). On the live dev overlay one change (6 sockets preset on/off) took **2.3–4.1 s**; with this branch it takes **0.55–0.7 s** (CDP profile, same config).

What was slow, and the fix (no behaviour change):
- **Price lookups**: the safety net audit and the Loot tab asked the same (group, base) thousands of times. `memoLookup` caches each lookup's answers; a new lookup is made whenever prices change.
- **Gem band rescue** (`compileCurrency`): ran over every item for every hidden band and re-parsed conditions each time. Bands are now computed once and indexed by base.
- **Levelling floors** (`lvFloor`): the "does this rule touch these items" check is cached per rule; grouped lists are built in place (`pushTo`) instead of copied on every add (quadratic for thousands of gems).
- **Edits and price moves**: `blocksOf` scanned all rules once per edit (176 edits). While edits and price moves apply it reads from a by-type index, rebuilt when an edit inserts a clone.

Reviewed adversarially by a separate reviewer: no behaviour differences found. Targeted vitest files pass locally; full suite on CI.
